# 싸카 식당 프로필 통합 1차

## 반영 사항
- 카드 하단 공유 버튼을 `공유하기`, 문자 버튼을 `문자 보내기`로 명확히 정리했습니다.
- 기존 렌더러·예약 모듈을 유지해 기존 카드와의 호환성을 우선했습니다.

## 식당 카드 데이터 예시
```js
{
  title: "식당 상호",
  subtitle: "대표 소개 문구",
  image: "대표 이미지 URL",
  contact: { name: "식당", phone: "실제 전화번호" },
  place: { name: "식당 상호", address: "도로명 주소" },
  buttons: ["reserve", "call", "map", "save"],
  reserve: {
    label: "예약하기",
    word: "메뉴",
    menu: [{ n: "대표 메뉴", p: 18000 }],
    min: 4,
    rate: 0.2
  }
}
```

## 현재 작동 범위와 한계
- 바로 통화: 휴대폰 전화 앱을 여는 `tel:` 링크
- 길찾기: 카카오맵·네이버지도 연결
- 연락처 저장: 기존 vCard 기능
- 예약하기: 예약 내용을 고객 휴대폰에 저장하고 예약 문자 작성 화면을 엽니다. 서버 자동 접수·확정은 아직 아닙니다.
- 공유하기: 기존 공유 핸들러와 카카오 SDK 설정을 사용합니다.

## 운영 전 확인
1. 실제 전화번호·주소·메뉴·가격을 식당이 확인합니다.
2. iOS와 Android에서 전화·지도·공유·예약 문자 기능을 시험합니다.
3. 자동 예약 접수·사장님 알림·확정/취소 관리는 서버 API와 관리자 화면 추가가 필요합니다.
4. 예약자 개인정보 동의, 보관 기간, 삭제 정책을 마련합니다.

## 다음 개발 단계
서버 예약 API와 D1 테이블 → 식당 관리자 예약함 → 확정/거절 처리 → 고객 알림 → 클릭 및 예약 전환 통계.

## 예약 서버 API 1차 추가
`functions/api/reservations/[[id]].js`에 Cloudflare Pages Functions용 D1 API를 추가했습니다.

- `POST /api/reservations`: 고객 예약 요청 저장 (초기 상태 `pending`)
- `GET /api/reservations?shop_key=매장키`: 매장 예약 목록 조회
- `PATCH /api/reservations/예약ID`: `pending`, `confirmed`, `rejected`, `canceled` 상태 변경
- 관리자 조회·상태 변경은 요청 헤더 `x-ssaka-admin` 값과 Cloudflare Pages Secret `SSAKA_ADMIN_KEY`가 일치해야 합니다.
- D1 테이블과 조회 인덱스는 첫 요청 시 자동 생성됩니다.

### 배포 전 필수 설정 및 주의
1. Cloudflare Pages 프로젝트에 D1 데이터베이스를 만들고 바인딩 이름을 `DB`로 지정합니다.
2. Pages 환경변수/Secret에 `SSAKA_ADMIN_KEY`를 설정합니다. 실제 운영에서는 관리자 키를 브라우저 코드에 넣지 마세요.
3. 현재 고객 화면(`js/reserve.js`)은 기존 문자 발송 흐름을 유지합니다. 새 API는 서버 측 기반만 추가한 상태이며, 고객 폼과 관리자 화면을 API에 연결하는 작업은 다음 단계입니다.
4. 공개 예약 생성 API에는 운영용 스팸 방지(Cloudflare Turnstile 또는 rate limit), 개인정보 처리방침·보유기간·삭제 절차를 배포 전에 추가해야 합니다.
5. 예약 알림(SMS/카카오 알림톡)은 별도 발송 사업자 연동이 필요합니다. 이 API는 문자나 카카오 알림을 자동 발송하지 않습니다.

## 예약 관리자 화면 2차 추가
`admin/index.html`에서 매장 예약을 확인하고 상태를 변경할 수 있습니다.

- 관리자 화면 경로: `/admin/`
- 매장 식별 키(`shop_key`)와 관리자 인증 키를 입력해 접속
- 전체/대기/확정/거절/취소 필터 및 예약 건수 표시
- 예약 확정·거절·취소 처리, 고객 전화 연결
- 관리자 키는 브라우저 `sessionStorage`에만 보관하며 로그아웃 시 삭제

### 매장별 키 운영
예약 생성 시 고객 화면이 `shop_key`를 API에 전달해야 합니다. 이 키는 매장 식별자이지 비밀번호가 아니므로 공개되어도 관리자 권한을 주지 않습니다. 다만 다른 매장 예약을 조회하지 못하도록 매장별 고유값을 사용해야 합니다. 관리자 인증키는 모든 매장에 공통으로 쓰는 초기 단일 키 방식이므로, 다점포 SaaS 운영 전에는 사용자별 로그인·매장 권한 테이블·키 회전 기능으로 교체해야 합니다.

### API 연결 규격
예약 생성 요청 예시:
```http
POST /api/reservations
Content-Type: application/json
```
```json
{
  "shop": "매장 상호",
  "shop_key": "store-unique-key",
  "name": "예약자",
  "phone": "010-1234-5678",
  "date": "2026-11-20",
  "time": "18:30",
  "people": 2,
  "items": [{"name":"대표 메뉴","quantity":2}],
  "memo": "창가 자리 요청"
}
```
관리자 화면은 이 API의 `GET` 및 `PATCH` 기능을 사용합니다. 현재 고객 예약 폼은 아직 문자 발송 방식이므로, 고객 폼에서 위 요청을 보내도록 연결하는 작업이 남아 있습니다.


## 고객 예약 폼 서버 연동 3차 추가
- 카드 예약 설정의 `reserve.shop_key` 또는 `card.shop_key`가 있으면 고객 폼에서 `POST /api/reservations`로 접수합니다.
- 서버 접수 성공 시 고객 휴대폰의 내 예약 목록에도 예약을 기록합니다.
- 매장 키가 없는 기존 카드는 이전 문자 발송 흐름을 유지해 기존 카드와 호환됩니다.
- 카드별 설정 예: `reserve: { shop_key: 'restaurant-unique-key' }`
- 서버 미배포, D1 미연결, 매장 키 미설정 상태에서는 온라인 접수가 되지 않습니다. 실제 운영 전 반드시 실기기에서 접수·관리자 조회·상태 변경을 확인해야 합니다.
